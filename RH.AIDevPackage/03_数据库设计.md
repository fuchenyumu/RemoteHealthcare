# 数据库设计方案（业务扩展版）

## 1. 技术栈与命名规范

- **数据库**：PostgreSQL 16（与平台管理库保持一致）
- **Schema**：沿用`public`，通过业务前缀区分表（`purest_rc_`）
- **命名规则**：
  - 表命名：`purest_rc_{业务域}`，与现有系统管理表的`purest_`前缀保持一致
  - 主键：`id bigint`，统一使用`nextval`序列
  - 公共字段：`create_by`、`create_time`、`update_by`、`update_time`、`remark`
  - 状态/类型字段：统一使用字典表`purest_dict_category`/`purest_dict_data`维护
- **数据访问**：后端通过SqlSugar 5.1.4映射实体，采用软删除和审计字段与平台保持一致

## 2. 业务域与表关系概览

```
purest_rc_patient_case        ← 患者快照信息
        ↑ 1..N
purest_rc_patient_pack        ← 调阅/打包记录
        ↑ 1..N
purest_rc_consultation        ← 远程会诊主表
        ├── purest_rc_consultation_member      （参与方）
        ├── purest_rc_consultation_attachment  （影像/病历等资料）
        ├── purest_rc_consultation_timeline    （流程轨迹）
        └── purest_rc_consultation_report      （会诊结论与签名）

purest_rc_sync_task           ← 院内系统数据同步任务
```

## 3. 核心表结构设计

### 3.1 患者会诊快照表 `purest_rc_patient_case`

```sql
CREATE SEQUENCE IF NOT EXISTS purest_rc_patient_case_seq START WITH 10000;

CREATE TABLE purest_rc_patient_case (
    id bigint NOT NULL DEFAULT nextval('purest_rc_patient_case_seq'),
    create_by bigint NOT NULL,
    create_time timestamp(0) NOT NULL,
    update_by bigint,
    update_time timestamp(0),
    remark varchar(1000),
    his_patient_id varchar(50),
    his_visit_id varchar(50),
    patient_name varchar(40) NOT NULL,
    patient_sex varchar(2) NOT NULL,
    patient_birth date,
    patient_type varchar(20) NOT NULL,
    id_card varchar(64),
    phone varchar(30),
    contact_address varchar(200),
    medical_summary text,
    allergies text,
    gestational_weeks numeric(4,1),
    child_age_months integer,
    data_source varchar(30) NOT NULL,
    CONSTRAINT pk_purest_rc_patient_case PRIMARY KEY (id)
);

COMMENT ON TABLE purest_rc_patient_case IS '远程会诊患者快照（含同步数据）';
COMMENT ON COLUMN purest_rc_patient_case.patient_type IS 'patient_type字典：RC_PATIENT_TYPE';
COMMENT ON COLUMN purest_rc_patient_case.data_source IS '数据来源（HIS/LIS/PACS/EMR/MANUAL）';
```

> **设计要点**
> - 保存会诊时刻的患者快照，避免院内主数据变更导致历史记录失真。
> - `patient_type`、`data_source`均通过字典维护，便于前后端统一。

### 3.3 远程会诊主表 `purest_rc_consultation`

```sql
CREATE SEQUENCE IF NOT EXISTS purest_rc_consultation_seq START WITH 10000;

CREATE TABLE purest_rc_consultation (
    id bigint NOT NULL DEFAULT nextval('purest_rc_consultation_seq'),
    create_by bigint NOT NULL,
    create_time timestamp(0) NOT NULL,
    update_by bigint,
    update_time timestamp(0),
    remark varchar(1000),
    case_id bigint NOT NULL,
    pack_id bigint,
    apply_org_id bigint NOT NULL,
    apply_doctor_id bigint NOT NULL,
    target_org_id bigint,
    target_department varchar(50),
    target_expert_id bigint,
    purpose text NOT NULL,
    emergency_level varchar(20) NOT NULL,
    consultation_status varchar(20) NOT NULL,
    desired_start_time timestamp(0),
    desired_end_time timestamp(0),
    scheduled_start_time timestamp(0),
    scheduled_end_time timestamp(0),
    meeting_room_no varchar(50),
    rtc_channel_id varchar(64),
    rtc_vendor varchar(30),
    audit_doctor_id bigint,
    audit_time timestamp(0),
    audit_comment varchar(500),
    close_reason varchar(500),
    CONSTRAINT pk_purest_rc_consultation PRIMARY KEY (id),
    CONSTRAINT fk_rc_consultation_case FOREIGN KEY (case_id) REFERENCES purest_rc_patient_case (id),
    CONSTRAINT fk_rc_consultation_pack FOREIGN KEY (pack_id) REFERENCES purest_rc_patient_pack (id)
);

COMMENT ON TABLE purest_rc_consultation IS '远程会诊主表';
COMMENT ON COLUMN purest_rc_consultation.emergency_level IS '紧急程度字典：RC_EMERGENCY_LEVEL';
COMMENT ON COLUMN purest_rc_consultation.consultation_status IS '会诊状态字典：RC_CONSULT_STATUS';
```

> **关联说明**
> - `apply_org_id`、`target_org_id`引用`purest_organization.id`
> - `apply_doctor_id`、`target_expert_id`、`audit_doctor_id`引用`purest_user.id`
> - `pack_id`可为空，表示尚未完成资料打包

## 4. 字典项配置

依托`purest_dict_category`和`purest_dict_data`，新增以下分类：

| 分类编码 | 名称 | 说明 |
| --- | --- | --- |
| RC_PATIENT_TYPE | 患者类型 | 孕妇、儿童、其它 |
| RC_PACK_STATUS | 打包状态 | 待打包、打包中、已完成、已过期 |
| RC_CONSULT_STATUS | 会诊状态 | 草稿、待审核、驳回、待排期、已排期、会诊中、已完成、已关闭 |
| RC_EMERGENCY_LEVEL | 紧急程度 | 普通、紧急、特急 |
| RC_MEMBER_ROLE | 会诊成员角色 | 主持人、专家、观察员、秘书 |
| RC_MEMBER_STATUS | 成员状态 | 待确认、已确认、会诊中、已退出 |
| RC_ATTACHMENT_TYPE | 资料类型 | 病历、检验、影像、其他 |
| RC_SOURCE_SYSTEM | 数据来源 | HIS、LIS、PACS、EMR、上传 |
| RC_TIMELINE_EVENT | 流程事件 | 提交申请、审核通过、审核驳回、排期完成、会诊开始、会诊结束、报告签署、关闭申请 |
| RC_REPORT_STATUS | 报告状态 | 草稿、签署中、已签署、已归档 |
| RC_SYNC_TYPE | 同步类型 | 患者资料、检验报告、影像、会诊报告 |
| RC_SYNC_STATUS | 同步状态 | 待执行、执行中、成功、失败 |

> 建议在`03_配套配置文件/数据库脚本`中补充批量插入脚本，确保初始化数据与字典保持一致。

## 5. 视图与索引设计

- **视图**：
  - `vw_rc_consultation_overview`：联结会诊、患者、打包、最新报告，供前端列表/统计使用。
  - `vw_rc_member_detail`：关联`purest_user`、`purest_organization`展示成员详情。
- **索引**：
  - `purest_rc_consultation`：`idx_rc_consult_status`（status）、`idx_rc_consult_org`（apply_org_id,target_org_id）、`idx_rc_consult_doctor`（apply_doctor_id）
  - `purest_rc_consultation_member`：`idx_rc_member_consult`（consultation_id）、`idx_rc_member_user`（user_id）
  - `purest_rc_consultation_attachment`：`idx_rc_attachment_type`（attachment_type）
  - `purest_rc_consultation_timeline`：`idx_rc_timeline_event`（event_code）

## 6. 数据安全与合规

- **敏感字段**：`id_card`、`phone`需使用`pgcrypto`或应用层加密，数据库存储密文；提供脱敏视图便于报表
- **审计追踪**：
  - 利用平台现有`purest_request_log`记录会诊相关API操作
  - `purest_rc_consultation_timeline`保存业务事件轨迹满足等保要求
- **会诊资料归档**：附件文件对接对象存储，`file_id`指向`purest_file_record`，在归档/删除时同步更新

## 7. SqlSugar 实体映射约定

- 所有业务实体继承平台公共实体（包含`Id`、`CreateBy`等字段），序列按`{TableName}Seq`命名
- 使用`SugarTable`、`SugarColumn`标注表名/字段名，枚举值统一绑定字典编码
- 时间字段统一转换为`DateTime?`，遵循UTC+8（数据库存UTC）

## 8. 数据流与同步

1. **患者调阅**：
   - 调用院内中间件 → 写入`purest_rc_sync_task`（status=待执行）
   - 中间件完成同步后更新`task_status=成功`，填充`snapshot`到`purest_rc_patient_case`
2. **资料打包**：
   - 成功同步后生成`purest_rc_patient_pack`，关联文件列表存入`purest_rc_consultation_attachment`
3. **会诊流程**：
   - 申请 → 审核 → 排期 → 音视频 → 报告签署
   - 每个关键动作写入`purest_rc_consultation_timeline`
4. **报告归档**：
   - 报告签署完成后，将报告元数据推送院内EMR，生成`purest_rc_sync_task`记录同步结果

## 9. 初始化脚本说明

- 新增脚本文件：`03_配套配置文件/数据库脚本/purest_rc_business.sql`
- 内容包含：
  1. 各序列+表结构定义
  2. 索引、外键约束
  3. 字典分类与数据插入语句
- 执行顺序：
  1. 先执行`admin-postgresql.sql`初始化平台表
  2. 再执行`purest_rc_business.sql`叠加业务表

---

通过以上设计，业务数据层与现有PurestAdmin系统管理数据实现统一风格，支持远程会诊全流程的资料调阅、排期、音视频协同、结论归档及统计分析需求，并兼顾SqlSugar实体映射、字典配置和后续扩展性。
